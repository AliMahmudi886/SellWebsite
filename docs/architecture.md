# معماری و تصمیم‌ها

## نسخه‌ی اول

- **Next.js 16 / React 19 / TypeScript**: رندر سمت سرور و App Router برای فراداده و صفحات قابل نمایه‌سازی، با API هم‌مخزن. نسخه‌ها در `package.json` ثابت شده‌اند.
- **Zod 4**: اعتبارسنجی ورودی سفارش روی سرور.
- **PostgreSQL با `pg` و SQL migrationهای نسخه‌بندی‌شده**: ثبت سفارش، اقلام، رخدادهای وضعیت، دسته‌بندی‌های مستقل و کاتالوگ را نگه می‌دارد. transaction و row lock از ثبت سفارش با موجودی کهنه جلوگیری می‌کند. نام دسته به محصول با foreign key متصل است؛ تغییر نام آبشاری انجام می‌شود و حذف دسته‌ی مصرف‌شده رد می‌شود. migration: `db/migrations`; seed توسعه: `scripts/seed.mjs`.
- **برندینگ** در `src/lib/store-config.ts` متمرکز است. محصولات نمونه در `src/lib/products.ts` قرار دارند. تصاویر hero و محصول در `public/images/` محلی و WebP هستند؛ تصاویر محصول نمایشی و تولیدشده‌اند، نه عکس مستند کالای واقعی.
- پرداخت فقط ثبت درخواست و هماهنگی دستی/پرداخت هنگام تحویلِ توافقی را نشان می‌دهد. پرداخت آنلاین، تأیید پرداخت یا هزینه/زمان ارسال به‌صورت ساختگی پیاده نشده است.

## مسیر تولید

پیش از استفاده‌ی عملیاتی، عکس‌های واقعی هر کالا را جایگزین تصاویر نمونه کنید، زمان‌بندی و محل امن خارج از دستگاه برای نسخه‌های پشتیبان تعیین کنید و تست رقابت موجودی/مجوزها را بیفزایید. ابزارهای dump/restore و تمرین در DB موقت در `scripts/db-backup*.mjs` و `scripts/db-restore*.mjs` هستند. عکس‌های `storage/uploads/` در dump دیتابیس نیستند و جداگانه backup شوند. درگاه آنلاین فقط پس از بررسی مستند رسمی جاری و افزودن idempotency/callback فعال شود.

## امنیت و محدودیت‌ها

- endpoint سفارش فقط فیلدهای مجاز را می‌پذیرد، تعداد و موجودی را در transaction بررسی می‌کند، اندازه‌ی درخواست را محدود می‌کند و قیمت را از کاتالوگ سرور می‌گیرد.
- مدیر از `ADMIN_EMAIL` و hash رمز bcrypt پیکربندی می‌شود؛ session امضاشده‌ی `jose` هشت‌ساعته، HttpOnly، SameSite Strict و در production Secure است. APIهای تغییردهنده session و origin یکسان می‌خواهند.
- آپلود مدیر فقط JPEG/PNG/WebP را با signature، اندازه‌ی بدنه و ابعاد محدود می‌پذیرد؛ Sharp metadata را حذف و خروجی WebP را به `storage/uploads/` می‌نویسد. فایل از `/api/media/<uuid>.webp` سرو می‌شود و مسیر دیسک باید در میزبان persist/backup شود.
- محدودسازی تلاش‌های ورود، سفارش، پیگیری و آپلود در PostgreSQL به‌صورت پنجره‌ی اتمیک مشترک بین workerها نگه‌داری می‌شود؛ در نبود دیتابیس فقط fallback حافظه‌ای همان process در دسترس است. `TRUST_PROXY=true` فقط پس از بررسی زنجیره‌ی پراکسی فعال شود. `TRUST_PROXY_HOPS` تعداد hopهای مورداعتماد از سرور به سمت بیرون است؛ انتخاب IP در XFF با این فاصله از انتهای زنجیره انجام می‌شود و هر عضو باید IP معتبر باشد. هدر نامعتبر، بیش‌ازحد بلند یا زنجیره‌ی کوتاه به سهمیه‌ی مشترک می‌افتد. مقدار پیش‌فرض یک hop است؛ در حالت بدون proxy درخواست‌ها همگی سهمیه‌ی مشترک دارند.
- فرم تماس/ایمیل نمایشی است و به سامانه‌ای ارسال نمی‌شود.
- سایت برای استقرار روی Node.js پشتیبانی‌شده و self-host آماده است. هاست‌های SSR و دیتابیس را بر اساس محل استقرار، دسترسی ایران، قوانین، هزینه و قرارداد جاری خود ارزیابی کنید؛ سرویسی خودکار انتخاب یا فعال نشده است.

## منابع رسمی بررسی‌شده

- Next.js، استقرار: https://nextjs.org/docs/app/getting-started/deploying
- Next.js، self-hosting: https://nextjs.org/docs/app/guides/self-hosting
- Next.js، سرآیندهای HTTP: https://nextjs.org/docs/app/api-reference/config/next-config-js/headers
- node-postgres، transaction: https://node-postgres.com/features/transactions
- PostgreSQL، `SELECT ... FOR UPDATE`: https://www.postgresql.org/docs/current/sql-select.html

در این نسخه درگاه ایرانی اضافه نشده است؛ پیش از انتخاب آن باید مستند رسمی همان ارائه‌دهنده، پذیرندگی و callback جاری جداگانه بررسی شود.

آخرین بررسی وابستگی‌ها: `npm audit --omit=dev --audit-level=high` صفر آسیب‌پذیری production گزارش کرد. audit کامل ۱۶ مورد متوسط در ابزارهای توسعه‌ی ESLint/minimatch نشان می‌دهد؛ `npm audit fix` آن‌ها را برطرف نکرد و npm فقط راهکار breaking با `--force` پیشنهاد داد، پس خودکار اعمال نشد.
