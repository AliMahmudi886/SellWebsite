# خانه‌ی نارنج — پایه‌ی فروشگاه آنلاین

پایه‌ی فروشگاه تک‌مشتری فارسی و راست‌چین با کاتالوگ، ثبت و پیگیری محرمانه‌ی سفارش و پنل مدیر. پیش از انتشار واقعی، مقصد استقرار، HTTPS، backup/restore، سیاست داده و rate limiting توزیع‌شده را تنظیم کنید.

## نیازمندی

- Node.js نسخه‌ی ۲۰ یا جدیدتر و npm.
- Docker Desktop و Compose برای دیتابیس محلی پیشنهادی است. PostgreSQL 16 در Compose فقط روی `127.0.0.1:5433` گوش می‌دهد. بدون `DATABASE_URL`، فروشگاه با داده‌ی نمونه نمایش داده می‌شود و فرم سفارش خطای موقت می‌دهد.

## نصب و اجرا

```powershell
npm install
Copy-Item .env.example .env.local
npm run dev
```

سپس `http://localhost:3000` را باز کنید. برای فعال‌کردن سفارش پایدار و پنل:

1. `.env.local` را از `.env.example` بسازید و `POSTGRES_PASSWORD` را با یک مقدار تصادفی عوض کنید. در `DATABASE_URL` همان رمز را URL-encode کنید.
2. `docker compose --env-file .env.local up -d` را اجرا کنید؛ دیتابیس مستقل روی پورت `5433` بالا می‌آید.
3. `DATABASE_URL`, `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH`, `ADMIN_SESSION_SECRET` را در `.env.local` تنظیم کنید.
4. اطلاعات تماس اختیاری فروشگاه را فقط بعد از تأیید واقعی در `NEXT_PUBLIC_SUPPORT_PHONE`، `NEXT_PUBLIC_SUPPORT_HOURS` و `NEXT_PUBLIC_INSTAGRAM_URL` قرار دهید. برای این مقادیر از شماره‌ی قابل تماس، ساعت پاسخ‌گویی واقعی و نشانی کامل `https://www.instagram.com/...` استفاده کنید؛ تا وقتی تنظیم نشده‌اند، سایت اطلاعات ساختگی نمایش نمی‌دهد.
5. رمز هش‌شده‌ی مدیر را با `npm run admin:hash` در ترمینال تعاملی بسازید؛ ورودی رمز echo نمی‌شود. مقدار `ADMIN_SESSION_SECRET` را محلی بسازید، مثلاً `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`. secret را در چت یا Git نگذارید.
6. `npm run db:migrate` و سپس `npm run db:seed` را اجرا کنید. seed در `NODE_ENV=production` متوقف می‌شود و رکوردهای موجود را بازنویسی نمی‌کند.
7. وارد `/admin` شوید. مدیر از env خوانده می‌شود؛ نقش‌های چندگانه در این MVP وجود ندارد.

برای اجرای smoke test دیتابیس، ابتدا سرور production را در یک ترمینال اجرا کنید (`npm run build` و `npm run start`) و در ترمینال دوم `npm run smoke:db` را اجرا کنید. تست سفارش و پیگیری، سه خرید تحویل‌شده‌ی مصنوعی برای پیشنهاد محصول، رتبه‌بندی صفحه‌ی جزئیات، و پاک‌سازی داده‌های آزمایشی را بررسی می‌کند.

هر کارت محصول به صفحه‌ی `/product/<id>` می‌رود. «محصولات مرتبط» از اقلام مشترک در سفارش‌های تحویل‌شده پیشنهاد می‌دهد؛ برای کاهش افشای الگوهای کم‌نمونه، هم‌خریدی باید دست‌کم در سه سفارش مستقل دیده شده باشد. تا قبل از آن، دسته‌بندی و نزدیکی قیمت fallback هستند. پیشنهادها سمت سرور ساخته می‌شوند و اطلاعات مشتری به مرورگر ارسال نمی‌شود.

بدون `DATABASE_URL` فروشگاه کاتالوگ خالی و پیام آماده‌سازی نشان می‌دهد و API ثبت سفارش با `503` پاسخ می‌دهد؛ بنابراین کالای نمونه به مشتری واقعی نمایش داده نمی‌شود و سفارش موفق جعلی نمی‌شود. داده‌های نمونه فقط با اجرای seed روی دیتابیس توسعه اضافه می‌شوند. سفارش دارای کد پیگیری تصادفی است؛ برای پیگیری، کد را در body به `POST /api/orders/track` بفرستید. API فقط وضعیت/اقلام را می‌دهد. کد را محرمانه نگه دارید.

برای ساخت نسخه‌ی اجرایی:

```powershell
npm run lint
npm run typecheck
npm test
npm run build
npm start
```

## پشتیبان‌گیری و بازیابی

پس از بالا بودن Docker database، با `npm run db:backup` یک dump فشرده در `backups/` بسازید. برای تمرین بازیابی بدون دست‌زدن به دیتابیس اصلی، `npm run db:restore:drill` یک پشتیبان تازه می‌سازد، آن را در دیتابیس موقت جداگانه restore و چند جدول کلیدی را می‌خواند، سپس دیتابیس موقت را حذف می‌کند.

برای بررسی فایل‌ها و دیدن پیشنهاد نگه‌داری ۱۰ نسخه‌ی معتبر جدیدتر، `npm run db:backup:prune` را اجرا کنید. این فرمان به‌طور پیش‌فرض فقط پیش‌نمایش می‌دهد؛ فایل نامعتبر را حذف نمی‌کند. حذف نسخه‌های قدیمی فقط با اجرای صریح `npm run db:backup:prune -- --keep 10 --apply --confirm-delete` انجام می‌شود.

بازیابی واقعی دیتابیس اصلی مخرب است و فقط با تأیید نام دیتابیس اجرا می‌شود. ابتدا Next.js را متوقف کنید، سپس مسیر فایل و مقدار دقیق `POSTGRES_DB` را بدهید:

```powershell
npm run db:restore -- backups/shop-....dump --confirm sellwebsite
```

اسکریپت پیش از تغییر، از دیتابیس فعلی یک dump با پیشوند `pre-restore-` می‌سازد، فایل را در دیتابیس موقت restore و اعتبارسنجی می‌کند، سپس دیتابیس‌ها را جابه‌جا می‌کند. دیتابیس قبلی با نام `*_before_*` باقی می‌ماند تا پس از بررسی بتوانید rollback کنید. فایل‌های `backups/` در Git نادیده گرفته می‌شوند؛ آن‌ها حاوی اطلاعات مشتری و سفارش‌اند، پس پوشه را در محل امن رمزگذاری‌شده نگه دارید. عکس‌های `storage/uploads/` بخشی از dump دیتابیس نیستند و جداگانه باید پشتیبان‌گیری شوند.

## شخصی‌سازی

- نام، توضیح، مبلغ/واحد، شهر، تماس، شبکه اجتماعی و رنگ برند: `src/lib/store-config.ts`.
- محصولات نمونه و قیمت‌ها: `src/lib/products.ts`.
- متن‌ها و تصاویر دمو: `src/components/storefront.tsx`.
- دسته‌بندی‌ها از پنل مدیر و جدول مستقل مدیریت می‌شوند؛ نام دسته در فرم محصول انتخاب می‌شود و کارت‌ها/فیلتر فروشگاه از دسته‌های موجود استفاده می‌کنند.
- تصاویر نمونه‌ی محلی WebP در `public/images/` ساخته شده‌اند تا فروشگاه به شبکه‌ی تصویر بیرونی وابسته نباشد. این‌ها عکس‌های نمایشی تولیدشده‌اند، نه مستندات واقعی اقلام فروشی؛ قبل از فروش، عکس کالای واقعی را جایگزین کنید.
- رابط از فونت متغیر فارسی Vazirmatn استفاده می‌کند که از مخزن رسمی دریافت و با `next/font/local` در build بسته‌بندی می‌شود؛ زمان اجرای سایت برای فونت درخواست خارجی ندارد. مجوز OFL همراه فایل در `public/fonts/OFL.txt` است.
- آیکون‌های رابط SVG محلی از مجموعه‌ی Lucide هستند؛ مجوز ISC در `public/icons/LICENSE.txt` نگه‌داری می‌شود.
- مدیر می‌تواند در پنل محصول JPEG، PNG یا WebP تا ۵ مگابایت بارگذاری کند. سرور نوع فایل را بررسی، metadata را حذف و تصویر را به WebP حداکثر ۱۸۰۰ پیکسلی تبدیل می‌کند. فایل‌ها در `storage/uploads/` ذخیره و از API محلی سرو می‌شوند؛ این پوشه عمداً در Git نیست و باید در backup محیط میزبان گنجانده شود.

## متغیرهای محیطی

از `.env.example` شروع کنید. `.env.local` وارد Git نمی‌شود. `NEXT_PUBLIC_SITE_URL` برای metadata، sitemap و robots است. `DATABASE_URL`, `DATABASE_SSL`, `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH` و `ADMIN_SESSION_SECRET` در برنامه استفاده می‌شوند. مقدار secret را در چت یا commit قرار ندهید.

در آخرین بررسی، audit production صفر یافته‌ی امنیتی داشت؛ audit کامل ۱۶ مورد متوسط را در ابزارهای توسعه‌ی ESLint/minimatch گزارش کرد. اصلاح خودکار آن‌ها تغییر شکننده پیشنهاد می‌داد و اعمال نشد.

## سفارش، پرداخت و موجودی

فرم checkout مبلغ را فقط در سرور از کاتالوگ PostgreSQL محاسبه می‌کند؛ ثبت سفارش، snapshot اقلام، رزرو موجودی و رخداد اولیه در یک تراکنش انجام می‌شود. لغو سفارش موجودی را برمی‌گرداند. پرداخت واقعی انجام نمی‌شود؛ پرداخت دستی/هنگام تحویل نیازمند هماهنگی است و وضعیت آن به معنی پرداخت موفق نیست. هزینه و زمان ارسال با مشتری هماهنگ می‌شود.

## حریم خصوصی و انتشار

اطلاعات سفارش در دیتابیس و فایل‌های عکس مدیر در `storage/uploads/` روی دیسک ذخیره می‌شوند. در استقرار میزبان باید این مسیر persistent و پشتیبان‌گیری شود؛ در container موقت بدون volume فایل‌ها از دست می‌روند. سیاست دوره‌ی نگهداری، حذف داده، بکاپ رمزگذاری‌شده و آزمون بازیابی هنوز باید برای کسب‌وکار تنظیم شوند. محدودسازی ورود مدیر، ثبت سفارش، پیگیری و آپلود در PostgreSQL مشترک بین workerها ذخیره می‌شود. `TRUST_PROXY=true` را فقط وقتی فعال کنید که معماری proxy را بررسی کرده‌اید؛ `TRUST_PROXY_HOPS` تعداد proxyهای مورداعتماد را از سمت سرور مشخص می‌کند (۱ برای یک proxy). proxy باید IP اتصال واقعی را به زنجیره اضافه کند یا هدر ورودی را بازنویسی کند. زنجیره‌ی خراب/نامعتبر یا کوتاه‌تر از مقدار تنظیم‌شده به سهمیه‌ی مشترک می‌رود. هیچ مخزن Git، remote، سرویس پولی یا استقرار عمومی در این پوشه تنظیم نشده است.

برای بررسی سفارش‌های نهایی قدیمی، `npm run db:privacy:retention -- --older-than-days 365` فقط پیش‌نمایش می‌دهد. هیچ بازه‌ی پیش‌فرض کسب‌وکاری اعمال نمی‌شود. اجرای بی‌نام‌سازی نیازمند `--apply --confirm-anonymize <POSTGRES_DB>` است؛ در production علاوه بر آن باید `ALLOW_PRODUCTION_PRIVACY_MAINTENANCE=true` را آگاهانه تنظیم کنید. فقط سفارش‌های تحویل‌شده/لغوشده‌ی پیش از بازه انتخاب می‌شوند؛ سفارش‌های باز محفوظ‌اند. نام، تلفن و نشانی پاک می‌شوند و کدهای پیگیری باطل می‌شوند، اما مبالغ، اقلام و تاریخچه‌ی وضعیت باقی می‌مانند. این ابزار backupهای قبلی را ویرایش نمی‌کند؛ حذف داده از backupها باید طبق سیاست backup میزبان جداگانه انجام شود.

## راه‌اندازی نشست جدید مدیر و MFA

پیش از راه‌اندازی نسخه جدید، مدیر را در یک محیط آزمایشی آماده کنید. نسخه جدید نشست JWT قبلی را نمی‌پذیرد؛ مدیر باید دوباره وارد شود. حساب مدیر فعلی همچنان از ADMIN_EMAIL و ADMIN_PASSWORD_HASH خوانده می‌شود. ADMIN_SESSION_SECRET برای مشتق کلید محدودسازی نرخ استفاده می‌شود.

1. با ابزار تأییدشدهٔ مدیریت اسرار، یک کلید تصادفی Base32 با حداقل ۳۲ نویسه ایجاد کنید. آن را در ADMIN_TOTP_SECRET در secret store و در برنامهٔ authenticator مدیر با SHA-1، ۶ رقم و بازهٔ ۳۰ ثانیه وارد کنید. ساعت هر دو دستگاه باید همگام باشد. راز را در چت یا Git درج نکنید.
2. در صورت نیاز به بازیابی، کدهای مستقل ۱۶ بایتی تصادفی را به صورت ۳۲ نویسهٔ hex کوچک بسازید و نسخهٔ اصلی را در محل امن آفلاین نگه دارید. فقط هش SHA-256 هر کد را با جداکنندهٔ کاما در ADMIN_RECOVERY_CODE_HASHES قرار دهید. کد پس از مصرف دیگر قابل استفاده نیست. برای تعویض فهرست، کدهای جدید بسازید.
3. ADMIN_ROLE را تنظیم کنید. owner همهٔ مجوزهای فعلی، support سفارش‌ها، catalog محصولات و دسته‌ها و رسانه، و auditor گزارش فعالیت را دارد. این تنظیم فعلاً نقش همان یک حساب را انتخاب می‌کند.
4. با حساب آزمایشی، بیلد production و npm run smoke:admin-security را اجرا کنید. پیش از rollout، migration افزایشی 011 را روی مقصد با فرایند عادی اجرا کنید. سپس نسخه جدید را بالا بیاورید و ورود با کد و خروج را بسنجید.
5. برای رخداد دسترسی، از مسیر مصوب عملیات همهٔ نشست‌های همان مدیر را سمت سرور ابطال کنید و اسرار را بچرخانید. جداول admin_sessions و admin_mfa_claims اطلاعات نشست و مصرف کد را نگه می‌دارند. کد مصرف‌شده را برای استفاده دوباره فعال نکنید.

بازگشت: جداول افزوده‌شده برای کد قدیمی بی‌اثرند، اما بازگشت به نسخهٔ پذیرندهٔ JWT ممکن است نشست‌های قبلی را دوباره معتبر کند. برای rollback برنامه امنیتی، secret امضای قبلی را بچرخانید و مدیر را از نشست قدیمی خارج کنید.

برای اجرای smoke امنیت به Chrome و Playwright فقط در صورت فعال‌کردن تست UI نیاز دارید. پس از بیلد، متغیر SECURITY_PLAYWRIGHT_MODULE را روی مسیر مطلق index.mjs نصب Playwright بگذارید و npm run smoke:admin-security را اجرا کنید. اسکریپت روی PostgreSQL محلی schema موقت با دادهٔ ساختگی می‌سازد، تست‌های سفارش و آپلود را هم اجرا می‌کند و schema را در پایان پاک می‌کند. migration اصلاحی 012 در کنار 011 باید در rollout اجرا شود.

### پردازش رویدادهای سفارش

پس از migration 015، npm run outbox:dispatch حداکثر ۱۰۰ رویداد آماده را در یک اجرا به inbox داخلی PostgreSQL تحویل می‌دهد. OUTBOX_BATCH_SIZE تعداد را از ۱ تا ۱۰۰۰ تنظیم می‌کند. فرمان تعداد تحویل، تلاش مجدد و شکست نهایی را چاپ می‌کند و اگر رویدادی در همان اجرا به سقف ۸ خطا برسد، با کد ۱ پایان می‌یابد. failed_at و next_attempt_at وضعیت پردازش را نشان می‌دهند. فرایند دائمی و مصرف‌کنندهٔ بیرونی باید جداگانه در محیط مقصد تعریف شوند.

#### عملیات صف رویداد

- npm run outbox:status شمار رویدادهای آماده، منتظر، شکست‌خورده و تحویل‌شده، سن قدیمی‌ترین رویداد در انتظار و حداکثر ۲۰ شکست اخیر را به صورت JSON نشان می‌دهد.
- npm run outbox:requeue -- EVENT_UUID فقط رویداد مشخصی را که به شکست نهایی رسیده و تحویل نشده دوباره آماده می‌کند. پس از بررسی علت شکست اجرا شود. اگر رکورد واجد شرایط نباشد، فرمان با کد ۱ پایان می‌یابد.
- npm run outbox:watch پردازش پیوسته را در یک فرایند جدا اجرا می‌کند. OUTBOX_POLL_MS از ۲۵۰ تا ۶۰۰۰۰ میلی‌ثانیه و پیش‌فرض ۵۰۰۰ است. تنظیم سرویس، restart و دریافت لاگ به محیط استقرار تعلق دارد. برای پایش، روی وجود شکست نهایی و افزایش سن صف هشدار تعریف کنید.

### استقرار پایش Outbox

پردازشگر watch را به‌عنوان فرایند جدا با همان نسخهٔ برنامه و پس از migration 015 اجرا کنید. روی Linux می‌توان از نمونهٔ systemd زیر پس از تطبیق مسیر و هویت سرویس استفاده کرد. DATABASE_URL از فایل محرمانهٔ محیط مقصد تأمین شود.

    [Unit]
    Description=Khaneh Narenj order outbox
    After=network-online.target
    Wants=network-online.target

    [Service]
    User=narenj-worker
    WorkingDirectory=/srv/narenj/current
    EnvironmentFile=/etc/narenj/outbox.env
    ExecStart=/usr/bin/node scripts/order-outbox-worker.mjs watch
    Restart=on-failure
    RestartSec=5
    TimeoutStopSec=30

    [Install]
    WantedBy=multi-user.target

پایش بیرونی در هر دقیقه npm run outbox:health را اجرا کند. وجود شکست نهایی یا رویدادی که حداقل ۱۲۰ ثانیه بعد از موعد پردازش همچنان آماده مانده، خروج ۱ می‌دهد. OUTBOX_MAX_READY_AGE_SECONDS حد را تغییر می‌دهد. تأخیر برنامه‌ریزی‌شدهٔ retry به تنهایی هشدار نمی‌دهد. خطای اجرای فرمان یا اتصال DB نیز شکست پایش است و باید بررسی شود. هنگام هشدار، ابتدا outbox:status و لاگ فرایند را ببینید و سپس رویداد مشخص را پس از رفع علت بازگردانید.
